## Running it

The `.bas` files are plain ASCII source. `petcat` (ships with VICE) tokenizes
them into a `.prg`, and x64sc autostarts a `.prg` — it LOADs **and** RUNs:

```sh
petcat -w2 -o tone.prg -- src/c64/tone.bas   # -w2 = BASIC v2 tokenized prg
x64sc tone.prg                                # boots, loads, RUNs automatically
```

`.prg` files are build artifacts (gitignored); the `.bas` is the source of
truth. Sanity-check a conversion by detokenizing back: `petcat -2 -- tone.prg`.

### Pushing into a running instance

You can only inject into a *live* emulator if you launched it with a socket
open. Start one with the text monitor:

```sh
x64sc -remotemonitor &   # opens a monitor on TCP 6510
nc localhost 6510        # load prgs into RAM, poke bytes, inspect registers
```

(There's also `-binarymonitor` on TCP 6502 — a binary protocol, better for
driving it programmatically.) This scriptable socket → emulator is the stand-in
for the eventual serial → real C64 link.

## Sound demo

The source lives in [`../src/c64/sound-demo.bas`](../src/c64/sound-demo.bas),
nabbed from [c64-wiki.com/wiki/SID](https://www.c64-wiki.com/wiki/SID). It loops
forever, picking a random waveform each pass and sweeping the pitch. Abort with
RUN/STOP.

### SID registers

The base address is `S = 54272` (`$D400`). Everything here drives **Voice 1**,
whose registers sit at offsets 0–6.

| POKE | Offset | Register | Value | Meaning |
|---|---|---|---|---|
| `poke s+24,15` | 24 | Filter mode / **volume** | 15 | Master volume max, no filter |
| `poke s+5,97`  | 5  | **Attack / Decay**       | 97  | Attack=6, Decay=1 |
| `poke s+6,200` | 6  | **Sustain / Release**    | 200 | Sustain=12, Release=8 |
| `poke s+4,w`   | 4  | **Control** (waveform + gate) | W | Waveform select + gate on |
| `poke s,x`     | 0  | Frequency low byte       | x   | Sweeps the pitch |
| `poke s+1,255-x` | 1 | Frequency high byte     | 255-x | Sweeps inversely |

The trailing `poke s+24,0` just slams volume to 0 to silence the note.

### Voices and their offsets

The SID has **three identical voices**, each a 7-register block. Everything above
addresses **Voice 1** (offsets 0–6). Voices 2 and 3 are the same registers shifted
up by 7 and 14, so the absolute address is **`S` + voice_base + register_offset**:

| Voice | Base offset | Base addr (dec) | Base addr (hex) | First register | Last register |
|---|---:|---:|---|---|---|
| 1 | +0  | 54272 | `$D400` | `s+0`  | `s+6`  |
| 2 | +7  | 54279 | `$D407` | `s+7`  | `s+13` |
| 3 | +14 | 54286 | `$D40E` | `s+14` | `s+20` |

So the per-voice register you want is `s + base + n`, where `n` is the same 0–6
offset from the Voice 1 table above (0/1 = freq lo/hi, 4 = control, 5/6 = ADSR,
etc.). A couple of worked examples:

- Voice 2 control (gate + waveform) → `s+7+4` = `poke s+11,17`
- Voice 3 frequency high byte → `s+14+1` = `poke s+15,...`

The filter/volume registers at `s+21`..`s+24` are **global**, not per-voice — one
master volume and one filter shared by all three voices. Only the 0–6 block
repeats. Reaching all three voices is what makes [chords](#playing-a-chord)
possible. The full per-voice map (with decimal/hex absolute addresses) is in the
[SID register reference](sid-registers.md#voice-base-addresses).

### Waveforms (register 4)

Register 4 selects the waveform in its high bits and carries control flags in the
low bits. Each waveform is a single bit; bit 0 is the **gate** (1 = start note /
trigger the envelope's attack). So the "bloody numbers" are just
`waveform_bit + 1`:

| W | Binary | Waveform |
|---|---|---|
| 17  | `0001 0001` | Triangle + gate |
| 33  | `0010 0001` | Sawtooth + gate |
| 65  | `0100 0001` | Pulse (square) + gate |
| 129 | `1000 0001` | Noise + gate |

`W` defaults to 17 (triangle); the random branch may overwrite it. The gate bit
in every value is what actually kicks off the envelope.

### ADSR

The envelope spans two registers, each holding two 4-bit nibbles
(high nibble / low nibble):

- **Reg 5 = 97** → `$61` → Attack=6, Decay=1
- **Reg 6 = 200** → `$C8` → Sustain=12, Release=8

The attack/decay/release numbers are indices into the SID's fixed timing tables,
not milliseconds; sustain is a *level* (0–15), not a time:

- **Attack 6** ≈ 68 ms to ramp to peak
- **Decay 1** ≈ 24 ms to fall to the sustain level
- **Sustain 12** ≈ hold at ~12/15 of peak while the gate stays on
- **Release 8** ≈ 300 ms to fade once the gate clears

In this program the note is cut by forcing volume to 0 rather than by releasing
the gate.

## Triggering a note

Setting the gate bit to 1 is what *triggers* the note — but on its own it's
silent. For an audible, continuous tone you need four things set first:

1. **Volume** (`s+24`) — zero by default, so no sound otherwise.
2. **Sustain** (`s+6` high nibble) — must be non-zero, or the envelope decays
   straight to silence and won't hold.
3. **Frequency** (`s+1`, optionally `s`) — the pitch.
4. **Control** (`s+4`) — waveform select + the gate bit (the `+1`).

Minimal continuous tone, in [`../src/c64/tone.bas`](../src/c64/tone.bas):

```basic
10 s = 54272
20 poke s+24,15 : rem volume = max
30 poke s+6,240 : rem sustain=15, release=0 ($f0)
40 poke s+1,17  : rem frequency high byte (pitch)
50 poke s+4,17  : rem triangle + gate on -> tone starts and holds
```

It plays forever. To stop, clear the gate bit (keep the waveform, drop the +1)
with `poke s+4,16`, or just kill volume with `poke s+24,0`.

## Colours

Sound is the SID's job; colour is the **VIC-II's**. The C64 has a fixed
16-colour palette (values 0–15) that you POKE into the VIC-II colour registers.

### The 16 colours

| Value | Colour | Value | Colour |
|---:|---|---:|---|
| 0 | Black | 8 | Orange |
| 1 | White | 9 | Brown |
| 2 | Red | 10 | Light red / pink |
| 3 | Cyan | 11 | Dark grey (grey 1) |
| 4 | Purple / violet | 12 | Medium grey (grey 2) |
| 5 | Green | 13 | Light green |
| 6 | Blue | 14 | Light blue |
| 7 | Yellow | 15 | Light grey (grey 3) |

### The colour registers you can POKE

`c` is a colour value 0–15 from the table above.

| POKE | Address | Hex | What it sets |
|---|---:|---|---|
| `poke 53280,c` | 53280 | `$D020` | **Border** colour |
| `poke 53281,c` | 53281 | `$D021` | **Background** colour (screen) |
| `poke 53282,c` | 53282 | `$D022` | Background 1 (multicolour text mode) |
| `poke 53283,c` | 53283 | `$D023` | Background 2 (multicolour text mode) |
| `poke 53284,c` | 53284 | `$D024` | Background 3 (multicolour text mode) |
| `poke 53285,c` | 53285 | `$D025` | Sprite multicolour 0 (shared) |
| `poke 53286,c` | 53286 | `$D026` | Sprite multicolour 1 (shared) |
| `poke 53287+n,c` | 53287–53294 | `$D027`–`$D02E` | Sprite *n* colour (n = 0–7) |
| `poke 646,c` | 646 | `$0286` | Current **cursor / text** colour |

**Character colour RAM** lives at `55296`–`56295` (`$D800`–`$DBE7`) — one byte
per screen cell (40×25 = 1000 cells), so `poke 55296+row*40+col,c` colours an
individual character.

Classic startup look:

```basic
10 poke 53280,14 : rem light blue border
20 poke 53281,6  : rem blue background
30 poke 646,14   : rem light blue text
```
